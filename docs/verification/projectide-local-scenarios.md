# Fixed-base local Scenario preparation

Existing scope: #1032 under #907/#905/#906/#908 and #888 SCEN/IMPACT/SEM contracts. This implements a local shared Core hypothesis, a Windows pure ViewModel journey and an Angular consumer of actual Core-prepared snapshots. It does not close #1032 or its actual paired UI/Backend acceptance.

ProjectScenarios.Prepare takes one exact admitted committed/candidate input and explicit ScenarioId/ScenarioRevisionId. The original Source stays immutable. Initial typed overrides replace Task duration, Task input defaults or Milestone targets through the existing value/declaration decoders. They cannot edit permissions, audit records or a shared Resource. Unknown values remain Unknown. Unsupported declarations/contracts cannot be overwritten through this API. All requested changes publish atomically or return an explicit refusal.

The canonical local overlay binds the exact base Source/input/context and ordered target/kind/port/value assumptions. Its domain-separated digest supplies the existing ScenarioRef and CompilerInputManifest scenario binding. This is an ephemeral local preparation format, not adoption of a formal Artifact schema/Registry. Caller-provided IDs do not allocate or register a durable version; a host must independently enforce version uniqueness and current authority. The same frozen request reconstructs the same input. At most 128 overrides and 262144 combined value/location UTF-8 bytes are admitted before cloning. Existing Source/settings encoding and execution bounds remain unchanged.

Revise requires the original exact base and a new Scenario revision. Rebase is explicit, keeps ScenarioId, creates a new revision/input and refuses changed overridden fields, missing targets, another Branch or a substituted Source body for the same immutable base context. Unrelated base changes are retained. Neither operation reuses earlier Compile/Test results. Materialize rejects another input or another Source body.

ToDraft requires the caller's separately supplied exact current base and an explicitly supplied new proposal candidate. Committed bases fork from their exact revision; candidate bases continue only the same proposal/base/captured target head with a fresh candidate ID. Known pinned or reserved contexts are refused. Only the supported concrete Source values are converted; scenario settings are removed and the original fixed engine/dependency/calendar/clock settings are retained. The plan applies to its exact base or nothing. It grants no durable Proposal creation, authorization, server save, review or shared Merge approval. A future capacity/availability/exclusion overlay cannot silently use this concrete-value conversion contract.

The Windows pure ViewModel previews and explicitly loads the hypothesis, clears old compilation/Tests and requests a fresh compile, retains separately labelled immutable baseline results and assumptions, and uses the existing shared semantic Source Diff. The host then runs the same local Project Tests on the new input. Source changes, assumptions and result axes stay separate. Conversion similarly requires the caller-supplied current base, creates a new Draft input and requests another compile/Test run. Selection, lifecycle, reset, disposal and synchronous notification reentry invalidate interrupted previews and preserve newer work. Baseline results are historical local values, never a live-authority claim.

Developer controls exercise an actual baseline TestFAIL -> Scenario TestPASS -> new Draft fresh TestPASS, fixed input/result identities, stale materialization and result rejection, deterministic override ordering, typed dates/durations, opaque Source preservation, explicit revision/rebase conflict, aggregate bounds and notification races. Invalid local-date fixture authoring initially caused five test failures; the fixture was corrected to include its existing typed calendar contract, without changing production semantics. Two additional negative tests reproduced and corrected same-version Source substitution and aggregate byte-bound gaps. Original failures remain retained and are not positive qualification.


The Angular preview recognizes the complete existing Scenario context: stable ScenarioId/revision, a committed/candidate fixed base and the overlay digest. It rejects nested Scenario bases, mixed identity fields and branch mismatch. A separate three-case profile is exported by actual Core Prepare/Materialize/ToDraft/Apply and fresh compilation/Tests. The primary31-case and Test editing2-case profiles remain unchanged. Users explicitly load a comparison, export its original canonical assumptions and move from the baseline to the Scenario to the prepared Draft. The panel separates declared assumptions, actual shared Core Source Diff and all three immutable Compiler/Test result bases; baseline CompilerPASS and TestFAIL remain distinct.

The reader verifies all three original Source/input/Test byte bindings, the canonical overlay digest, fixed settings, exact target values, candidate conversion bindings and both native comparison projections. Array-level port changes cannot conceal unrelated port/type/cardinality edits. Unknown local overlay fields and unsupported reference-origin transformations are refused rather than guessed. This is a consumer of a prepared example, not an arbitrary browser AST editor or a runtime execution/write endpoint. Derived views own their rows and recheck the complete captured materialization/metadata basis and member identities. Hashes are content checks, not producer attestation or current authority. Final generation/context/read checks apply after asynchronous admission and immediately before comparison publication, download or staged loading; denied/reselected contexts cannot restore old results or focus.


Explicit rebase now uses the same typed origin visitor as Draft fork/Rename/Scenario application. It advances exact local declaring origins in both the captured Before value used for conflict detection and the hypothetical replacement value. Reference target context/identity and manifest remain pinned; foreign origins, Unknown basis and absent optional values remain untouched. Nested nullable/optional/structure/list/sequence/set/map values use the existing shared types, and Set encoding retains canonical ordering. Real target/manifest/value changes still conflict; a missing or denied materialized snapshot cannot become TestPASS.

Two actual pinned-snapshot regressions reproduced the former defects: an existing reference default falsely conflicted when only its declaring context advanced, while an absent default allowed a rebased hypothesis to retain the old declaring origin. Both are corrected without changing reference resolution or authorization semantics. Developer controls also cover nested values, opaque reference-shaped Unknown basis, Set ordering with an independently foreign origin, fresh converted-Draft bindings and stale result rejection. These controls do not extend the Angular prepared reader to unsupported reference-origin transformations or establish runtime authority.

The shared Core can also read a bounded applied-value projection from an exact Scenario or converted Draft input. Each row retains the original canonical assumption bytes and their domain-separated digest, the actual typed value read from the applied Source, its original canonical bytes/digest, and the exact after-context target. The complete projection binds the overlay, base input, Scenario input, after input, after Source and after context. Substituted Source bodies, settings, stages or revisions are refused; projection processing can independently return ResourceLimit without invalidating the original plan. The 128-row and 262144 combined applied value/target UTF-8 bounds remain in force. Projection readiness proves neither reference resolution nor Compile/Test/Simulation PASS, producer attestation or current authority.

The existing three-case offline export now includes both Core projections. Angular checks their bounded original bytes, unique JSON members, exact fields and rows, assumption membership, actual after-Source values, all input/Source/context bindings and domain-separated hashes. Rehashed substitutions and post-admission projection changes are refused; the existing final lifecycle/selection checks still apply. This supplies the producer/consumer binding for applied values without implementing a browser canonicalizer or a second writable AST. The current scalar example and its original overlay remain unchanged; the main31 and Test editing2 profiles remain byte-identical. Reference-bearing projection controls run against actual authorized/materialized pinned snapshots in Core, including nested values, rebase and Draft conversion. The browser's existing refusal of reference-origin transformations remains until a complete admitted external-snapshot transport and native replay journey is supplied. Such browser reference acceptance is not claimed by these projection tests.
