# Explicit Test definition editing and repository interchange

Existing work: #1031, #1030 and #905 under #888 PTEST/CI-PROJ/SEM contracts. Project Source remains the single writable AST. A definition JSON file is an explicit export or import input; there is no watched second AST, automatic repository sync or new filename/folder ABI.

## Core transition

ProjectTestEditing.Export returns the canonical declaration bytes for one exact Test identity/document/current input. Unknown or invalid Test definitions can be exported losslessly with their decode status. Incomplete structural discovery, an ambiguous identity, stale input or wrong scope cannot claim a unique target.

Preview accepts a complete replacement for that same Test. The current four assertion families can be added, removed, reordered and edited through the existing typed decoder: Boolean, exact numeric comparison, collection count and reference resolution. EntityId, DocumentId ownership and declaration version remain stable. Invalid version-one assertions can be repaired; unsupported/future contracts cannot be silently overwritten or downgraded. Empty assertion lists remain valid Source and do not imply Test PASS.

An explicit proposal context either forks its exact committed base into a local candidate or advances a candidate in the same proposal/base/captured target head. Fresh candidate IDs cannot reuse known/pinned contexts. Typed references to the previous local context advance; pinned foreign contexts remain unchanged. The existing transition preserves opaque Source/document/manifest data and recomputes canonical document/manifest/Source/input digests. Previously decoded siblings cannot silently become invalid.

The immutable plan binds both inputs, Sources, contexts, target and original/imported/result declaration digests. ApplyToDraft returns the entire prepared snapshot only for its exact original input and Source. It grants no server save, Proposal registration, current authorization or shared Merge approval. The new candidate needs fresh compilation and Tests; old result input IDs cannot be reused.

## CLI

After building tools/ProjectIde.Tests, invoke its framework-dependent executable with:

~~~text
ProjectIde.Tests --export-test SOURCE_JSON INPUT_ENVELOPE_JSON ENTITY_ID NEW_DEFINITION_JSON
ProjectIde.Tests --preview-test-edit SOURCE_JSON INPUT_ENVELOPE_JSON ENTITY_ID DEFINITION_JSON NEXT_CONTEXT_JSON NEW_PLAN_JSON
~~~

The export is the canonical declaration itself. The explicit preview response contains the plan plus new canonical Source and its input envelope; it never rewrites the original Source, input, definition or lock. This supports caller-selected repository export paths without making files another authoritative AST. User edits are imported only through the typed preview, then applied as a new local candidate.

Exit 0 means definition export or edit preparation succeeded; it is not Test PASS. Exit 2 is an unavailable/refused/non-decision state, including NoChange or cancellation; exit 3 is invalid input/identity or I/O failure. The normal three-argument Test runner retains its existing Pass/Fail/non-decision/Error exit semantics.

All input files use the existing 4 MiB/depth 64 Source processing profile. A complete preview wrapper may contain multiple admitted snapshots and is separately bounded to 16 MiB/depth 68; this changes no Source, assertion or execution limit. Full encoding precedes CreateNew publication; existing output paths are preserved. No dependency restore, latest resolution, network execution or implicit evaluator adoption occurs. Data-only commands do not execute Tests. A later run uses the actual CLI binary-bound evaluator as before.

## Paired consumers

The Windows pure ViewModel exports definitions, previews arbitrary supported replacements and applies only its exact current preview to a newer local generation. Application clears old compilation, Tests, selections and edit state and requests a fresh compile. Selection/context/reset/disposal and synchronous notification reentry invalidate interrupted previews.

The offline Web preview has a separate two-case editing example generated by actual Core export, preview, application and compilation. The primary 31-case fixture is unchanged and the per-bundle 32-case limit is unchanged. The Web reader checks source/input/declaration byte bindings and the exact prepared candidate. Users can download the original canonical definition, inspect the proposed import and load the Core-prepared new Draft. This is an example-backed consumer, not arbitrary browser AST editing or a runtime write endpoint; Core/CLI and Windows pure APIs own the actual generic edit.

Both controls recheck current read admission, input/generation and exact prepared-member identity. A delayed hash result cannot restore an older candidate after a denied/context boundary. Definition export and candidate loading do not constitute independent Security qualification or evidence eligibility.
