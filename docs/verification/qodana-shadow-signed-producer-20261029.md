# Isolated Qodana signed-shadow producer qualification — 2026-10-29

**Target:** `SecurityTestImplimation` only. Tracked in [Issue #1500](https://github.com/NYGsatoshi/Coglatas/issues/1500). The original `main` Code Scanning, Qodana Community and Cloud analysis jobs are **unchanged**.

## Why an isolated signer rather than signing inside the Qodana analyzer

Qodana invokes a complex third-party .NET analyzer and repository-controlled bootstrap code. Giving that job GitHub OIDC signature authority would broaden its attack surface. The proposed workflow runs only on a named `SecurityTestImplimation` push with the fixed GitHub repository ID; no `pull_request`, `pull_request_target`, `workflow_run` or default-branch trigger is permitted.

Three independently isolated GitHub-hosted jobs implement the test:

1. **`shadow-producer` (read-only):** check out the exact integration SHA, validate existing workflow trust and Action pins, analyze using the same immutable Qodana Community image/action and zero Critical/unresolved-symbol policy, and run the existing project-model gate and exact-SHA SARIF provenance parser. Only on success, upload the **original unmodified SARIF file** for this run; no OIDC rights or Qodana Cloud token.
2. **`shadow-attestor` (the only OIDC/write job):** require successful producer; download the exact same-run original SARIF with the existing SHA-pinned download action; ensure the subject is present; invoke [`actions/attest` v4.2.2](https://github.com/actions/attest/releases/tag/v4.2.2) at immutable verified SHA `1e69f48acb82d1966a394da916b4c1698aa569d6`. Only this job has `id-token: write` and `attestations: write`, with `contents: read` and `actions: read`. Optional artifact storage-record creation is explicitly **disabled**. This signer runs no Qodana analyzer, no repository scripts and no Cloud API.
3. **`shadow-verification` (read-only):** require successful signer; download the original same-run SARIF; execute `gh attestation verify` with the fixed repository, signer workflow SHA, integration branch ref, source SHA and SLSA predicate; reject report digest/source/run/attempt/hosted-runner mismatches; publish only a bounded non-release receipt. No signing or Cloud credentials.

## Approval and trust registry

The existing SHA pin registry `governance/github-actions-allowlist.json` now records the verified signed upstream action commit. The established trust registry `governance/workflow-trust-policy.json` allows the **single** `shadow-attestor` job to request `id-token:write` and `attestations:write` for the **push** event only. The existing protected Main Qodana and Cloud jobs are not eligible for this permission.

PR checks must run `scripts/ci/test_qodana_shadow_signature.py` and `tests/ci/test_qodana_shadow_workflow.py` through the existing read-only GitHub Actions Static Analysis lane. The latter fails if a PR introduces a pull-request trigger, broadens the branch, grants the analyzer OIDC rights, enables storage-record writes, changes the immutable Action pin, skips the Qodana project-model guard or allows Cloud token use.

## Qualification limits

- On the candidate PR branch **the signing job does not run**; it is intentionally limited to a future push on `SecurityTestImplimation` after an approved PR merge. Passing PR static tests is not evidence that a real GitHub/Sigstore signature has been minted. The first integration push must produce a successful 3-job execution and a verified signed report; failed/queued/skipped shadow checks remain visible.
- GitHub's certificate validates the identity of the attestor workflow. Because the signing operation consumes an artifact generated by a distinct read-only producer, **it is not cryptographic proof of that producer's job identity**. The signed report is independent shadow evidence, not sufficient to reuse an existing Main Qodana Community report.
- The receipt always declares `producerJobAttested=false`, `mainProducerAttested=false`, `cloudReplayVerified=false`, `qualifiedForGateReuse=false`.
- Historic Qodana reports were signed by neither this shadow workflow nor Main's Community analyzer; they remain unqualified. Real Main producer attestation and actual Cloud ingestion are separately reviewed gates with separate authorization and policy changes.
- This shadow job can add ~25 minutes of runner time on a qualifying integration push; it is a one-off validation lane with narrow `paths`, **not a speed optimization or release clearance**.
